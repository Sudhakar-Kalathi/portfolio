Case study

Chit Fund Management System

Java 17 · Spring Boot · Spring Security · JWT · MySQL · React 18 · Vite

Overview

An application for running chit operations: customers, groups, monthly cycles (including auction/payout figures), contribution payments, a day book, and company payout tracking. GitHub describes it as a demo version of an audit-oriented chit fund system.

Problem

Chit workflows mix membership, monthly auctions, and money. Spreadsheets lose history, allow silent edits, and don’t enforce “this group is full” or “this payment is too old to change.”

Solution

A React client talks to a Spring Boot REST API. Services own the rules; JPA maps customers, groups, members, cycles, payments, day-book lines, and payouts onto MySQL.

Technology stack

Backend: Java 17, Spring Boot, Spring Security, JWT (jjwt), Spring Data JPA, MySQL, Maven, Bean Validation, Lombok. Frontend: React 18, Vite, React Router, Axios, Tailwind CSS.

Key features

  • JWT login; ADMIN vs STAFF authorization on API routes.
  • Customer create/search/detail with unique name, phone, and generated customer codes; soft-delete via an active flag.
  • Chit groups with duration aligned to member count; membership capped; monthly cycles created when a group is created.
  • Cycle updates for winner, auction amount, commission, dividend, and monthly payable amount.
  • Payment recording and a two-week restriction on editing older payment dates.
  • Day book credit/debit summaries with BigDecimal totals.
  • Company payout records tied to group cycles.

Architecture

React (Axios + JWT) → REST controllers → services (@Transactional) → Spring Data repositories → MySQL
Entities stay behind DTOs and mappers. GlobalExceptionHandler maps not-found, business, and duplicate errors to API responses.

Database

Core tables/entities: Customer, ChitGroup, ChitGroupMember, ChitCycle, Payment, DayBookEntry, CompanyPayout. Money fields use BigDecimal. Member relations use lazy fetches. Group names are unique; customers cannot be added twice to the same group.

API

  • POST /auth/login
  • GET/POST /api/customers and admin write routes under /api/admin/customers
  • /api/chit-groups including member attach and cycle update
  • POST /api/payments, payments by date and by month
  • /api/daybook and payout routes under /api

Business logic

  • On group create, total members is set from total months and empty monthly cycles are initialized.
  • Adding a member fails if the group is already at capacity or the customer is already enrolled.
  • Completing a cycle stores auction/payout numbers and marks the cycle completed.
  • Payment updates throw a business exception if the payment date is older than two weeks.

Engineering decisions

  • Stateless JWT instead of server sessions.
  • BCrypt password hashing; CSRF disabled for the token API.
  • DTOs so JSON does not leak raw entities.
  • Soft-delete flags on financial history rather than hard deletes.

Challenges

Keeping monthly cycles, membership limits, and money arithmetic consistent in one transaction path — especially when a cycle completion also relates to payout tracking. Using BigDecimal and @Transactional services was the practical answer in this codebase.

My contribution

I designed and implemented the backend modules, security configuration, and the React client that consumes the API. The public repository is under my GitHub account.

What I learned

Domain rules belong in services, not in the UI. Once group capacity and payment locks lived on the server, the frontend became a client of those rules instead of a second copy of them.

Case study

LearnSphere – E-Learning Platform

Java 17 · Spring Boot 3.2 · Spring Security · JWT · MySQL · HTML · CSS · JavaScript

Overview

LearnSphere is a full-stack e-learning demo: a Spring Boot REST API with JWT auth and MySQL, plus a static HTML/CSS/JS frontend. Local repository name: E-Learning-App. Public repo: e-learning-app.

Problem

A learning product needs more than a course list. Students enroll, instructors publish lessons, and an admin needs a view of users — each with different permissions on the same data.

Solution

Three roles (STUDENT, INSTRUCTOR, ADMIN) share one API. Method security (@PreAuthorize) gates student, instructor, and admin controllers. The catalog is public so marketing/course pages can load without a token.

Technology stack

Spring Boot 3.2.3, Spring Web, Spring Data JPA, Spring Security, MySQL, jjwt 0.11.5, validation. Frontend: multi-page HTML with shared main.js calling /api.

Key features

  • Register/login; JWT filter on authenticated routes.
  • Public catalog: list and course detail with lessons and assignments.
  • Students: enroll (duplicate enrollments rejected), view enrolled courses, submit assignment file URLs, progress percentage increased on submission.
  • Instructors: create courses they own; add lessons (contentUrl) and assignments; ownership checked before edits.
  • Admins: aggregate stats (users, courses, enrollments), user list with passwords stripped, delete user.
  • Demo users and sample courses seeded when the database is empty.

User flow

Browse catalog → sign up / log in → student enrolls → opens course lessons → submits assignments. Instructors stay on their dashboard to publish content. Admins open stats and the user list.

Technical implementation

Controllers talk to JPA repositories. Enrollment stores progressPercentage. Assignment submit upserts a Submission and bumps progress by 10 (capped at 100). Lesson video playback is a URL on the lesson entity, not a custom streaming service.

Architecture

HTML/JS pages → /api/auth, /api/catalog, /api/student, /api/instructor, /api/admin → Spring Security JWT → JPA → MySQL

Database

User (with Role), Course (instructor), Lesson, Assignment, Enrollment (student + course + progress), Submission.

API

  • POST /api/auth/register, POST /api/auth/login
  • GET /api/catalog/courses, GET /api/catalog/courses/{id}
  • POST /api/student/courses/{id}/enroll, enrollments, course detail, assignment submit
  • Instructor course/lesson/assignment create routes
  • GET /api/admin/stats, GET /api/admin/users

Engineering decisions

  • Public catalog vs authenticated role APIs, so the marketing pages do not require a session.
  • Role-specific HTML dashboards instead of a single SPA — simpler to ship as static files next to the API.
  • Passwords cleared before returning the admin user list.

Challenges

Keeping instructor writes scoped to courses they own (403 if the instructor id does not match). Enrollment must exist before a student can load private course detail or submit work.

My contribution

I built the Spring Boot API, security configuration, persistence model, and the static frontend pages that call it.

What I learned

Role checks are cheaper to reason about when they sit on the controller, not only in the UI. The UI can still fail closed if the API refuses the call.
